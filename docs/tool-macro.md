**Shirley technical design · Tool macro expressiveness (Tool Macro)**

> **Status: implemented.** The `#[tool]` function macro now supports optional companion hooks
> `on_register = fn_name` / `on_unregister = fn_name`, and the macro wires the hooks into the generated `impl Tool`.
> Contract tests are in `crates/shirley-agent-sdk/tests/tool_lifecycle.rs` (SDK side) and
> `src/tools/web_search.rs` (application side). For the trait-side mechanism, see `docs/tool-lifecycle.md`.
>
> The body of this document preserves the reasoning from the planning phase and the **rejected alternatives**; **the wording in the "final plan" section below is authoritative**.

**1. What this document answers**

The `#[tool]` macro originally could only generate **stateless** tools -- the `GenerateTool` it produced only held `definition`:

```rust
struct GenerateTool {
    definition: ::shirley_agent_sdk::ToolDefinition,
}
pub fn tool() -> impl ::shirley_agent_sdk::Tool + 'static {
    GenerateTool { definition: definition() }
}
```

Stateful tools could not be expressed with it: `todo` hand-writes `impl Tool` (holding an `Arc<TodoStore>`),
and `web_search` goes through `ToolContext` injection (the tool itself is still stateless, but needs "inject the dependency at registration time").

The user's question: **should the macro be refined or should something new be added? Is there a better way to express this?** The user's hard constraint is:
**"the macro is essentially about letting the user focus only on their own implementation, without having to care about tool details."**

---

**2. Draw a line first: the macro should only eliminate "boilerplate"**

Criterion -- **only things that every tool has to repeat writing, and whose content is entirely determined by the signature, should be generated by the macro**:

| Thing | Is it boilerplate | Should it go in the macro |
| --- | --- | --- |
| Argument JSON Schema | yes (determined by the argument types; `schemars` can derive it) | ✅ yes |
| Argument deserialization | yes (determined by the argument types) | ✅ yes |
| `ToolDefinition` assembly | yes | ✅ yes |
| State fields (`client` / `store`) | **no** (different per tool; the macro cannot guess the type) | ❌ no |

`on_register` / `on_unregister` sit in between -- **it is a "reference", not "generation"**: the macro does not generate the hook
semantics, it only wires the ordinary functions the user wrote onto `impl Tool`. What the user writes is still their own implementation (an ordinary
`fn(&mut ToolContext) -> Result<(), ToolError>`), and they do not touch the `Tool` trait.

---

**3. Root cause: the macro bundles two things together**

`#[tool]` does two things at once:

1. **Schema generation**: from typed arguments -> JSON Schema (+ deserialization).
2. **`Tool` impl generation**: produce the `GenerateTool` struct + `impl Tool`.

For stateless tools, bundling the two is fine. For stateful tools:

- #1 **still has value** (when hand-writing `impl Tool`, the `ToolDefinition`'s schema JSON is the most annoying boilerplate -- `todo` hand-wrote dozens of lines of `serde_json::json!`);
- #2 **forces statelessness** (the shape of `GenerateTool`'s fields is hard-wired).

---

**4. Alternatives and the final choice**

**Option A: leave the macro untouched; stateful tools hand-write `impl Tool`**

`todo` is already in this shape.

- **Pros**: zero macro changes; no new concept.
- **Cons**: the schema JSON for `definition` must be hand-written; **betrays "the user does not touch tool details"** -- the user is forced to write
  `impl Tool` and assemble `ToolDefinition`.

**Option B: split out a schema-generating derive macro (`#[derive(ToolArgs)]`), so hand-written tools can reuse it**

Add a new derive macro that **only generates the schema + deserialization**, not the `Tool` impl; stateful tools hand-write
`impl Tool` but no longer hand-write JSON.

- **Pros**: schema boilerplate reuse; the `Tool` impl is completely free.
- **Cons**: introduces a new macro (a derive macro), and **the user still has to hand-write `impl Tool`** -- likewise betraying the hard constraint.
  **Withdrawn.**

**Option C: a struct-level macro, one shot**

Upgrade `#[tool]` to accept functions and structs/impls at the same time, generating state fields + `impl Tool` + lifecycle.

- **Pros**: one macro unifies all tools.
- **Cons**: macro complexity explodes (parsing structs, impls, method attributes, distinguishing state fields vs arguments).
  **Not adopted.**

**✅ Final plan (implemented): extend the function macro + optional companion hooks**

Keep **one function macro** and give it two **optional** attributes:

```rust
#[tool(
    description = "search the public internet for the latest information...",
    on_register = web_search_on_register,
    on_unregister = web_search_on_unregister,
)]
pub async fn web_search(
    ctx: &ToolContext,
    #[param(description = "the query")] query: String,
) -> Result<String, ToolError> { /* ... */ }

/// Companion functions: ordinary fns; the user writes the implementation and does not touch the Tool trait.
fn web_search_on_register(ctx: &mut ToolContext) -> Result<(), ToolError> {
    let state = WebSearchState::from_env()
        .map_err(ToolError::ExecutionError)?
        .ok_or_else(|| ToolError::ExecutionError("DEEPSEEK_API_KEY not configured".into()))?;
    ctx.insert(state);
    Ok(())
}

fn web_search_on_unregister(ctx: &mut ToolContext) -> Result<(), ToolError> {
    ctx.remove::<WebSearchState>();
    Ok(())
}
```

The macro inserts overrides into the generated `impl Tool`:

```rust
fn on_register(&mut self, ctx: &mut ::shirley_agent_sdk::ToolContext) -> Result<(), ::shirley_agent_sdk::ToolError> {
    super::web_search_on_register(ctx)
}
```

- **The hook definitions still live on the `Tool` trait** (with empty default implementations); the macro only "references" them -- it does not move the lifecycle
  semantics into the macro.
- **No hook written = empty implementation**: stateless tools (`bash` / `read`) need **zero changes**.
- **The user only writes**: the tool function + an optional ordinary `fn`; they do not touch `impl Tool`, the schema, or the trait.
- The hook signature is fixed as `fn(&mut ToolContext) -> Result<(), ToolError>` -- determined by the `Tool` trait definition;
  the macro only references them by name.

---

**5. Why not A / B / C**

- **A / B both require the user to hand-write `impl Tool`**, directly violating the hard constraint "the macro is the only entry point, the user does not touch tool details".
- **C's macro complexity is severely mismatched with the current need** (there are currently only 2 stateful tools).
- The final plan leaves "wiring" to the macro (purely mechanical, no semantics) and "implementation" to the user (ordinary functions),
  landing exactly on the line in section 2: **the macro only eliminates boilerplate, it does not anticipate semantics.**

---

**6. The shape and division of labor of the function macro**

| | `#[tool]` (function, with optional hooks) |
| --- | --- |
| Input | one async function + optional companion hook function names |
| Output | a complete `Tool` impl (`GenerateTool`) |
| State | none (can inject into `ToolContext` via a registration hook) |
| lifecycle | wired by the `on_register` / `on_unregister` attributes; not written means an empty impl |
| Applies to | all tools (`bash` / `read` / `web_search`) |

There is only one macro. `todo`, because it needs to hold an `Arc<TodoStore>` and is internal to the SDK, still hand-writes `impl Tool` --
it is the only exception, not the paradigm.

---

**7. Execution semantics of the hooks (consistent with the trait side)**

- `on_register`: called by `ToolManager::register` after the duplicate check passes and before insertion; returning `Err` means registration fails and the
  tool does not enter the table (no half-registered state is left).
- `on_unregister`: `ToolManager::unregister` removes it from the table first, then calls back; **best-effort**, an `Err` only reports
  failure, and the tool is not resurrected. An unregistered name returns `ToolError::NotFoundError`.
- For details, see sections 4 and 5 of `docs/tool-lifecycle.md`.

---

**8. Blast radius**

| Item | Impact | Breaking |
| --- | --- | --- |
| `#[tool]` (function macro) | add **optional** attributes `on_register` / `on_unregister` | no |
| `macros` crate | `ToolConfig` gains two `Option<Ident>`; generate optional overrides | no |
| `Tool` trait | the two hooks are default empty methods | no |
| `ToolManager` | holds `ToolContext` + `unregister` | no |
| `web_search` | migrated to `#[tool]` + a registration hook | no |
| `todo` | unchanged (the only internal tool that hand-writes `impl Tool`) | no |
| Docs | this file + `docs/tool-lifecycle.md` + `docs/web-search.md` + `Agent.md` | no |

---

**9. Resolved decision points**

1. **Does lifecycle go into the macro**: ~~no~~ -> **yes, but in a "reference" way** -- the macro only wires ordinary functions the user wrote,
   and the semantics remain on the `Tool` trait. This is the intersection of the two constraints "the macro is the only entry point" and "the macro does not anticipate semantics".
2. **Is a derive macro needed**: **no**. Withdraw the `#[derive(ToolArgs)]` plan -- it requires the user to hand-write `impl Tool`.
3. **`#[tool]` generates `mod #name`, and the function must be at the same level as the mod**: **unchanged**; not handled this time (an existing constraint).

---

**10. Relationship to existing documents**

- This document is the **macro-side companion** to `docs/tool-lifecycle.md`: that one defines the lifecycle hooks (trait side), and this one defines
  how the macro wires the user-written companion functions onto the hooks.
- Boundary decisions follow item 4 of section 8 of `Agent.md`: schema generation / hook wiring are **generic mechanisms** (SDK/macro),
  while a specific tool's arguments and state are **application-layer**.
