# 文件补丁工具（`apply_patch`）

**状态：M1 已实现 + M2 的编辑栈已落地。** 落点在 `src/tools/apply_patch.rs`（应用层工具），
经 `bootstrap.rs` 注册；`/undo`、`/redo` 的应用层接线与 UI diff 渲染仍待做（见第九节）。

## 一、它是什么

`plan.md` 第 181 行提出的能力：

> 除了 bash，我们还要提供一个 apply_patch，这样我们就能直接观测到 Agent 本轮到底修改了什么，
> 同时我们能够将其发送到视图层消费。以及说可以运行回滚本轮改动，而不是仅仅通过 git diff。

所以 `apply_patch` **不是"又一个写文件的方式"**，而是一条**结构化、可观测、可回滚的改动通道**。

**在"编辑文件"这件事上，它必须取代 `bash`，而不是与 `bash` 并列。** 理由见下节——它的两个
核心保证（可观测、可回滚）只有在"所有编辑都经过它"时才成立；一旦 `bash` 还能改文件，这两个
保证就是假的。`bash` 仍然负责**执行**（跑测试、构建、查询），只是**不再负责改文件**。

它要同时满足三个诉求，这三个诉求决定了后面所有取舍：

1. **可观测**——改动要以结构化形式暴露给 UI，不能只回一句 `OK`。
2. **可回滚**——要能撤销本轮改动，所以必须留下"改前内容"。
3. **与 git 无关**——这是**硬约束**，见下。

### 与 git 无关（硬约束）

**Shirley 不替用户提交 commit**，因此编辑能力必须**完全自包含**，不能把 git 当作回滚或历史
的底座：

- 回滚**不靠** `git checkout` / `git restore` / `git revert`，靠我们自己的编辑栈。
- 工作区可能**根本不是 git 仓库**，甚至可能是 git 仓库的子目录。任何依赖 `.git` 的设计
  都会在这类环境下失效。
- git 只是用户可能并存的另一套工具。**我们不碰它、不假定它存在、不代替用户做提交决策**——
  "要不要提交、提交什么"是用户的判断，不是 Agent 的。

所以历史与回滚的真相来源是**我们自己的编辑栈**，而不是 git 的 reflog / 暂存区。

### 只适合纯文本（硬边界）

`apply_patch` 的全部前提——`@@` 锚点、` ` 上下文行、`+` / `-` 行——都建立在"文件是**文本**、
有**行**结构"之上。所以它的能力边界是硬的，必须**显式拒绝**而不是碰运气：

- **二进制文件直接拒绝**：图片 / 字体 / `.sqlite` / 编译产物 / 压缩包等没有"行"和"上下文"，
  补丁无从谈起。用与 `read_file` 相同的 NUL 探测（`BINARY_SNIFF_BYTES`）判定。
- **只处理 UTF-8**：非 UTF-8 文本（GBK / Latin-1）**明确报错**，绝不用 `from_utf8_lossy`
  有损转换——那会把文件悄悄改坏，正是要避免的。
- **BOM / 尾换行 / CRLF**：按文件现有形态处理，不擅自增删 BOM、不改尾换行、不统一换行符。

**推论（必须诚实交代）**：二进制资源的"修改"（换一张图、替换一个构建产物）**没有"编辑"语义，
只有"替换 / 生成"**——那属于 `bash` 的"执行"范畴。所以"编辑独占"要精确表述为：
**文本文件的编辑独占 `apply_patch`；二进制资源的替换 / 生成不适用补丁，走 `bash`**。
这不是给 `bash` 开后门，是承认补丁工具的物理边界。

### 为什么必须独占"编辑"角色（而不是和 bash 并存）

这是本设计最关键、也最容易被妥协掉的一点。

`apply_patch` 的价值**不是"能写文件"**（`bash` 早就能：`>` / `sed -i` / heredoc）。它的价值是
**可观测 + 可回滚**——而这两个保证都有一个共同前提：**编辑必须全部经过它**。

- **可观测会失效**：如果 `bash` 还能改文件，那 `sed -i` / `>` 重定向改了什么，视图层根本看不见，
  "本轮改了什么"就成了残缺的。一个能被绕过的观测点，等于没有观测点。
- **可回滚会失效**：绕过 `apply_patch` 的改动不进编辑栈，`/undo` 撤不掉。用户以为能回滚，
  实际回滚不干净——**这比没有回滚更危险**（虚假的安全感）。

因此立场是：**编辑只走 `apply_patch`**。这里的"取代"是**角色取代**，不是工具删除——
`bash` 与 `apply_patch` 职责正交：

| 能力 | 归属 | 说明 |
| --- | --- | --- |
| 执行命令（测试 / 构建 / 查询 / 探查） | `bash` | 只读式使用，不改工作区文件 |
| 修改工作区文件 | `apply_patch` | 唯一入口，保证可观测 + 可回滚 |

**诚实交代收敛手段与其边界**：技术上**无法硬阻止** `bash` 写文件（`echo x > f` / `sed -i` 防不住）。
沙盒管的是"能碰什么"（`docs/security.md`），管不到"用哪个工具改"。所以收敛靠**约定**而非强制：

1. `apply_patch` 的工具描述里写清"改文件用本工具，不要用 shell 重定向 / `sed -i`"。
2. 系统提示词（`src/prompt.rs`）里明确编辑纪律：编辑走 `apply_patch`，`bash` 只用于执行。
3. （可选，后续）`bash` 工具对明显的写文件形态做**软提示**（不拦截，只提醒），进一步降低误用。

> 这是有意的取舍：与其假装 `apply_patch` 有强制力，不如如实承认"这是约定"。但**约定必须写进
> 工具描述和系统提示词**——否则模型没有任何理由不用顺手的 `sed -i`。

## 二、为什么是应用层工具，不进 SDK

判定标准见 `Agent.md` 第八节第 4 条：SDK 只沉淀"下次做 Agent 还会用到"的基础能力。

- 它绑定"这个工作区 / 这台机器"，与 `bash` / `read_file` 同类，属于应用层。
- 它复用 SDK 已经提供的接缝——`#[tool]` 宏 / `Tool` trait / `ToolManager` / `ToolError` /
  `ToolContext` / `WorkSpace`，不需要新增 SDK 契约。
- "改动日志 + 回滚"是应用层的会话/视图能力，不是 SDK 的基础能力。

## 三、输入格式：Codex 风格上下文补丁，不用 unified diff

这是最关键的决策。三种候选：

| 方案 | 问题 |
| --- | --- |
| unified diff（`@@ -1,5 +1,7 @@`） | 要求模型算准行号与行数，LLM 极易写错；错一个数字整块失败 |
| old/new 字符串替换（edit 工具式） | 稳健，但多文件 / 多处改动非常啰嗦，且不天然产出 diff 供观测 |
| **Codex `apply_patch` 格式** | 上下文锚定、**不需要行号**、天然支持增删改，专为 LLM 设计 |

采用第三种。格式示例：

```text
*** Begin Patch
*** Update File: src/tools/read.rs
@@ fn workspace_root
     std::env::var("SHIRLEY_WORKSPACE")
         .ok()
         .filter(|value| !value.trim().is_empty())
+        .map(PathBuf::from)
*** Add File: src/tools/apply_patch.rs
+use shirley_agent_sdk::tool;
+...
*** Update File: src/tools/legacy_read.rs
*** Move to: src/tools/read_file.rs
@@ fn workspace_root
     ...
*** Delete File: src/tools/old_notes.txt
*** End Patch
```

`@@` 后面跟的是**锚点上下文**（函数名 / 附近行），模型只要复制它读过的内容即可，不用心算行号——
这正好匹配 `read_file` 返回带行号纯文本、"读一段改一段"的工作方式。

四种块（对齐 Codex）：

- `*** Update File: <path>`：后接若干 hunk。hunk 内行首 `+` 新增、`-` 删除、空格为上下文。
- `*** Add File: <path>`：整段为 `+` 行，文件不存在则新建。
- `*** Delete File: <path>`：删除文件。
- `*** Update File: <path>` + `*** Move to: <new_path>`：**重命名 / 移动**文件（可在移动的同时
  改内容）。`<new_path>` 同样受工作区约束。

> 路径一律**相对工作区根**，绝不接受绝对路径（与 `WorkSpace::resolve` 一致）。

## 四、参数与调用形态

签名极简，**只有一个参数**（格式自描述，不需要更多旋钮）：

```rust
#[tool(description = "对工作区内的**文本文件**应用补丁（二进制 / 非 UTF-8 会被拒绝）。\
    支持新增/更新/删除/重命名文件，用 *** Begin Patch / *** End Patch 包裹，块内以 \
    *** Update File: / *** Add File: / *** Delete File: 分段，重命名用 *** Move to:。\
    更新用 @@ 锚点定位，行首 + 为新增、- 为删除、空格为上下文；上下文请前后各保留约 3 行，\
    以确保唯一匹配。**改文件一律用本工具，不要用 shell 重定向 / sed -i**。改动是原子的：\
    任一 hunk 匹配失败则整体不落盘。**动手前请先用 read_file 读取目标文件**，补丁要基于文件\
    的真实内容。")]
pub async fn apply_patch(
    ctx: &ToolContext,
    #[param(description = "补丁文本，使用 *** Begin Patch 格式")] patch: String,
) -> Result<String, ToolError> { ... }
```

`ToolContext` 参数不进入 schema（由宏排除），用来挂改动日志（见第七节）——与 `web_search`
注入 state 是同一手法。

## 五、应用语义

这块最容易做坏，逐条钉死：

1. **先整体解析，再整体应用**。补丁 parse 成 `Vec<FileOp>`，任一语法错误直接 `ArgumentsError`，
   **一个字节都不写**。
2. **匹配：默认精确，允许"有界容错"**。hunk 的上下文行必须能在文件里**唯一找到**；
   找不到就失败，并在错误里回显**期望匹配的上下文**（对齐 Codex 的
   "Could not find match for hunk"），让模型自我纠正。
   - 允许**有界容错**：仅对**空白 / 缩进**不敏感（对齐 Aider / Claude Code），以降低
     模型复制上下文时缩进对不齐导致的失败率。
   - **但仍要求唯一匹配**；一旦用了容错，**必须在返回里显式标注**（用了哪处容错），
     绝不静默。
   - **绝不按位置猜**（不靠行号、不靠"最近似"乱配）——那会改错地方还看不出来，
     是这类工具最危险的地方。
3. **原子落盘**：写临时文件 + `rename` 替换（与 `src/session.rs::truncate` 同一套）。全成功才算成功。
4. **保留换行风格**：按文件现有的 `\n` / `\r\n` 处理，不统一改掉。
5. **新增文件**：路径必须在工作区内；父目录不存在则创建（减少往返）。

## 六、安全与工作区约束

复用 `read_file` 现成的护栏，保持两个工具口径一致：

- 每个路径都过 `WorkSpace::resolve`，绝对路径 / `..` 越界 → `ArgumentsError`。
- 疑似密钥文件（`.env` / `*.pem` / `id_rsa*` 等，复用 `read.rs::is_secret_file`）**默认拒绝写入**——
  否则模型可能把密钥写进仓库。
- 补丁体大小上限 + 目标文件大小上限（防一次改动灌爆上下文 / 磁盘）。
- 二进制文件拒绝。

> 顺带：`workspace_root()` 目前在 `bash.rs` 与 `read.rs` 各抄了一份，`is_secret_file()` 在 `read.rs`。
> 落地时应把这两个抽到 `src/tools/` 的公共位置（如 `mod.rs` 或 `util.rs`），避免三处漂移。

## 七、可观测性 + 回滚：自包含编辑栈（undo / redo）

这是让工具"不只是写文件"的关键。历史与回滚的承载结构是**编辑栈**（undo / redo），
而不是一份只追加的日志。注册时（`on_register` 钩子）注入状态：

```rust
struct PatchState { stack: Arc<Mutex<EditStack>> }

/// 一次 apply_patch 调用 = 一个栈帧（可能含多文件），保证帧级原子回滚。
struct EditFrame {
    changes: Vec<FileChange>,
}

struct FileChange {
    path: PathBuf,
    before: Option<Vec<u8>>,  // None = 新建（undo 时删除该文件）
    after: Option<Vec<u8>>,   // None = 删除（undo 时重建该文件）
    added: usize,
    removed: usize,
}

struct EditStack {
    undo: Vec<EditFrame>,  // 已应用、可撤销
    redo: Vec<EditFrame>,  // 已撤销、可重做
}
```

**为什么是栈而不是日志**：日志只追加、只够展示 diff；栈支持 `push`（应用补丁）/ `pop`
（undo）/ 再 `push` 到 redo 栈（redo），语义从"记录"变成"可逆操作序列"。应用一个新补丁时
**清空 redo 栈**（经典 undo 语义：新分支覆盖旧的重做路径）。

**粒度**：一次 `apply_patch` 调用（可能多文件多 hunk）= 一个 `EditFrame`。undo 一次撤掉整帧
（保证原子性），不会出现"半个补丁"。

**存快照还是存操作**：对 Coding Agent 这种"文件不算巨型、但要求回滚绝对可靠"的场景，
采用 **memento（改前/改后快照）为主**——`before` / `after` 保证回滚与 redo 都稳；
`added` / `removed` 作为 command 元信息，供 UI 展示。不用"重放操作"做 redo，因为重放依赖
上下文匹配，容易失败。

三个消费方：

- **给模型**：返回纯文本摘要（改了哪些文件、各 `+N/-M`），模型能据此汇报 / 自纠。
- **给 UI**：应用层从 `PatchState` 读出当前帧的 `FileChange` 列表，渲染成本轮 diff。正好接上
  `plan.md` 的"发送到视图层消费"，且与 `wire.rs` 追加 `ToolStarted` / `ToolFinished` 字段的
  思路一致（对外契约不膨胀）。
- **回滚 / 重做**：**不做成工具**（模型不该自己撤销自己），而是应用层操作——`/undo` 弹一个
  `EditFrame`、用 `before` 恢复文件（`before == None` 则删除）、压入 redo 栈；`/redo` 反向。
  这样实现"回滚本轮改动"，且**全程与 git 无关**。

> 注意：`EditStack` 是内存态，跨进程重启会丢——与 recall / todo 的"无持久化"是同类技术债，
> v0 可接受，先记在这里。若要持久化，落到会话日志（`docs/session.md`）里，而**不是** git。

## 八、错误分类（照 `ErrorKind` 语义走）

| 情形 | 归类 | 理由 |
| --- | --- | --- |
| 补丁语法错误 / 上下文匹配失败 / 路径越界 / 密钥文件 | `ArgumentsError` | 都是请求侧问题，模型换个写法 / 重读就能成功 |
| 磁盘 IO 失败、临时文件 `rename` 失败 | `ExecutionError` | 环境问题，不是模型能修的 |

分类给重试决策用，**不 match 字符串**——延续项目现有约定（`docs/plan.md`、`docs/runtime-hardening.md`）。

### 失败必须响亮，绝不吞错

"保证编辑成功"和"失败响亮"是一体两面：**尽最大努力提高命中率，但一旦真失败，绝不假装成功**。
三条硬规则：

1. **失败一律返回 `Err(ToolError)`**，绝不返回"部分成功"的字符串。多文件补丁里任一文件失败 =
   整体失败，工作区回到调用前（原子性），而不是"改了 3 个、失败 1 个"再回一句 `OK`。
2. **禁止吞错**：实现里不许 `let _ = ...` / `.ok()` / `.unwrap_or_default()` 把解析 / IO 错误
   静默掉；所有失败路径冒泡成结构化错误。**回滚（undo）失败也必须报错**，不能假装撤销成功。
3. **错误必须可行动**：报错要说清——哪个文件、哪个 hunk、**期望匹配什么**（回显上下文）、
   为什么。模型才能据此自我纠正。

> 这与上一条"有界容错"不冲突：容错是为了**提高成功率**，响亮是它**失败后的底线**。

## 十、已知坑 / 决策备忘

- **在编辑上 `apply_patch` 必须取代 `bash`**：不是"两个写文件工具并存"，而是"编辑唯一走
  `apply_patch`"。若允许 `bash` 改文件，可观测 + 可回滚两个保证同时失效（见第一节）。`bash`
  继续负责执行，但不再负责改文件。
- **匹配失败必须响亮**：宁可报错让模型重读，也不要模糊匹配改错行。
- **原子性不是可选项**：半应用状态会让"回滚"直接失效。
- **只碰文本**：二进制 / 非 UTF-8 一律拒绝；二进制资源的替换 / 生成不适用补丁，走 `bash`
  （见第一节"只适合纯文本"）。
- **绝不吞错**：失败返回 `Err`、不返回"部分成功"、不用 `.ok()` / `unwrap_or_default()` 静默
  错误（见第八节）。
- **新增工具的原则**（`plan.md`）：能让 Agent 行为表现更好才值得新增。`apply_patch` 的价值在
  "可观测 + 可回滚"，不在于"能写文件"（`bash` 本来就能写）。
- **覆盖写入折进补丁**：不做独立的整文件写工具（违背"原子化单点能力"），而是复用同一补丁里的
  `*** Delete File:` + `*** Add File:`（同路径、Delete 在前）= 覆盖。解析器把这一对合并成
  `Overwrite`；其它形式的重复路径（两次 Update、Add 在前 Delete 在后）仍拒绝。
- **中间目录可缺失**：`*** Add File: sub/new.txt` 这种"顺带建目录"是合理用法。SDK 的
  `WorkSpace::resolve` 要求父目录已存在，故 `apply_patch` 侧对 `Io(NotFound)` 做宽松解析
  （自展开 `.` / `..` 拒绝越界 → 向上找已存在祖先交 SDK 校验 → 拼回缺失尾部），落盘时
  `create_dir_all` 建目录。

## 十一、测试（落地时）

- 解析：三种块语法、非法补丁拒绝、缺 `Begin/End Patch` 拒绝。
- 应用：单 hunk / 多 hunk / 多文件；上下文不匹配时报错且**不改任何文件**；新增 / 删除。
- 应用：重命名 / 移动（`Move to`），移动 + 改内容。
- 安全：越界路径拒绝、密钥文件拒绝、二进制拒绝、**非 UTF-8 拒绝**、大小上限。
- 原子性：一个 hunk 失败 → 其余文件也保持原样（含"不返回部分成功"）。
- **不吞错**：解析 / IO 失败必须冒泡为 `Err`；回滚失败也必须报错。
- **有界容错**：仅空白 / 缩进差异时能匹配，且返回里**显式标注**用了容错；非空白差异仍失败。
- 换行风格：`\r\n` 文件改后仍是 `\r\n`；BOM / 尾换行不被改动。
- 宏生成的 schema 正确（只有 `patch`，`ctx` 不入 schema）；缺状态报未初始化。
- **覆盖写入**：`Delete` + `Add` 同路径合并为 `Overwrite`，端到端覆盖已有文件；其它重复路径拒绝。
- **中间目录缺失**：`Add File: sub/new.txt`（`sub/` 不存在）能成功并建目录。
- **编辑栈**：一次调用入一帧；`undo()` 还原、`redo()` 重放（内存态，进程结束即失）。


## 十二、对标主流方案

设计定稿前对照了三个主流 Coding Agent 的编辑工具。结论：**骨架无需推翻**（批量 + 原子 +
编辑栈 + 与 git 无关，这套组合是对的），几处细节对齐。

| 方案 | 编辑形态 | 关键取舍 |
| --- | --- | --- |
| Claude Code | `FileEditTool`（search-and-replace，默认）+ `FileWriteTool`（整文件，仅新建 / 重写） | `old_string` 必须**唯一出现**，否则报错要更多上下文；三原则：最小破坏性 / 可验证（明确 before/after）/ 抗幻觉（不存在的代码则失败） |
| OpenAI Codex | `apply_patch`（上下文补丁） | `@@` 锚点 + ` ` 上下文 / `-` 删 / `+` 增；块类型 `Add` / `Delete` / `Update` + `Move to`；一次多文件批量 |
| Aider | 多格式可切换 | `whole` / `diff`（`<<<<<<< SEARCH … ======= … >>>>>>> REPLACE`）/ `diff-fenced`（Gemini）/ `udiff`（简化 unified diff，给 GPT-4 Turbo，压 lazy coding）；**按模型选最优格式** |

**共同结论（我们踩对了）**：

1. **都回避 unified diff 的行号**（`@@ -1,5 +1,7 @@`）——LLM 算不准。改用**内容锚定**。
2. **都要求"改前先读过文件"**——命中率的前提。
3. **匹配失败要响亮**——回显找不到的上下文，让模型补更多上下文重试。
4. **最小破坏性 + 明确 before/after**——`EditStack` 的 `before` / `after` 覆盖。

**采纳的修订**：

- **有界容错**（见第五节）：对齐 Aider / Claude Code 的空白 / 缩进容错，降失败率。
- **`Move to` 重命名 / 移动**（见第三节）：对齐 Codex。
- **上下文前后各 3 行 + 改前先 read**（见第四节）：写进工具描述。

**未采纳**：

- **多格式可切换**（Aider）：我们锁定单一模型配置，暂不需要；但值得记一句——**格式选择本质是
  跟模型走的**，将来换模型若命中率差，可考虑引入。
- **独立的整文件写工具**（Claude Code 的 `FileWriteTool`）：不引入独立工具（违背"原子化单点能力"），
  但把"覆盖写入"折进补丁——`Delete File` + `Add File` 同路径 = 覆盖（见第十节）。新建大文件仍用
  整段 `+` 的 `Add File`，略啰嗦但可接受。
