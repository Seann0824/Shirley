**Shirley technical design · Adapter middle layer (P1)**

**1. Current state and two pieces of design debt**

`plan.md` itself pointed out two problems, and both are still there:

**Debt one: the location of `encode_messages`**

The comment in `chat_completions/mod.rs` (the line above the `encode_messages` definition):

> Honestly I feel this should be conversion logic done on the message side, rather than us writing it in the adapter layer for this message handling.

Right now the "internal Message -> protocol format" mapping is written in the adapter layer. Every protocol added means copying this mapping again, and the implementations of the various protocols tend to drift.

**Debt two: tool arguments have no middle layer**

The `#[tool]` macro directly generates OpenAI-format JSON Schema:

```rust
parameters: ::serde_json::json!(::schemars::schema_for!(Arguments)),
```

And `ToolDefinition.parameters` is just a bare `serde_json::Value`. So the argument structure is hard-wired to OpenAI, and it cannot be reused when switching to Anthropic's `input_schema`.

**2. Goal**

Introduce a "protocol-agnostic intermediate representation", and let each protocol be responsible only for two-way conversion. Criterion: **when adding a protocol, write only one conversion, and do not change the `Message` and `Tool` definitions.**

**3. Message side: a unified internal representation**

The `Message` enum itself is already a decent intermediate representation; the only problem is that the "encode into protocol format" step is in the wrong place. Plan:

```rust
// crates/shirley-agent-sdk/src/message/codec.rs (new)
pub trait MessageCodec {
    type Wire;
    fn encode(&self, message: &Message) -> Result<Self::Wire, CodecError>;
    fn decode(&self, wire: Self::Wire) -> Result<Message, CodecError>;
}
```

`chat_completions` implements `MessageCodec`, and `encode_messages` goes from a free function in the adapter layer to one of its methods. The adapter layer only does "get a `Message` -> call the codec -> send the request".

This way `chat_completions/mod.rs` slims down to pure protocol details (URL, headers, body assembly, SSE parsing), and the message mapping goes back where it belongs.

**4. Tool arguments: a standardized intermediate model**

This is the more critical layer. The core is to downgrade the schema generated by `#[tool]` from "OpenAI JSON Schema" to a "standard argument model", which each protocol then converts.

**4.1 Intermediate model**

```rust
// crates/shirley-agent-sdk/src/tool/schema.rs (new)
#[derive(Debug, Clone)]
pub enum ParamType {
    String,
    Integer,
    Number,
    Boolean,
    Array { items: Box<ParamType> },
    Object { fields: Vec<ParamField> },
    Optional(Box<ParamType>),
}

pub struct ParamField {
    pub name: String,
    pub description: String,
    pub ty: ParamType,
    pub required: bool,
    pub default: Option<serde_json::Value>,
}
```

**4.2 Macro-side changes**

The `#[tool]` macro generates `ParamType` instead of directly generating the schema. This can be done incrementally: first have the macro produce both (`schemars` schema kept for OpenAI, `ParamType` for other protocols), and only switch the main path after confirming it is correct.

Type mapping rules:

| Rust type | ParamType |
| --- | --- |
| `String` | `String` |
| `i32` / `i64` / `u64` | `Integer` |
| `f64` | `Number` |
| `bool` | `Boolean` |
| `Option<T>` | `Optional(T)`, with `required = false` |
| `Vec<T>` | `Array { items: T }` |
| `struct` (derives `JsonSchema`) | `Object { fields }` |

Note the semantics of `Option<T>`: `#[tool]` currently uses `Option<u64>` to mean "the argument may be omitted"; the macro needs to recognize `Option` as `required = false` rather than generating `nullable`.

**4.3 Protocol conversion**

```rust
// chat_completions
fn encode_tool_schema(field: &ParamField) -> Value { /* -> JSON Schema */ }

// anthropic
fn encode_tool_schema(field: &ParamField) -> Value { /* -> input_schema */ }
```

**5. Multi-protocol rollout**

The fix for the `todo!()` in `codec` is in `runtime-hardening.md`. Suggested order:

1. **Responses**: shares its origin with ChatCompletions, the differences are smallest, do it first. **Done** (`adapter/responses/`, including streaming; the plan is in `docs/responses-api.md`).
   **The detailed plan is in `docs/responses-api.md`** -- it pushes this section's "tool-argument standardization" conclusion one step further:
   Responses' `tools[].parameters` and ChatCompletions'
   `tools[].function.parameters` **both accept JSON Schema**, differing only by a wrapper. This confirms that
   JSON Schema itself is the cross-protocol intermediate representation, and there is no need to invent a `ParamType`; the real differences are in the **message
   item structure** and the **streaming event semantics**.
2. **Anthropic Messages**: needs to handle the standalone `system` field, the content-block structure of `tool_use` / `tool_result`, and the `thinking` block. The differences are the largest, so do it last.
   **Implemented** (`docs/anthropic-messages-api.md`, based on real packet captures). The three most fatal differences:
   tool results live in the **user message** (Anthropic has no tool role), `input_tokens` **does not include cache**
   (the opposite of OpenAI, so `cache_read` must be added back when mapping), and streaming tool arguments rely on **`input_json_delta`
   fragment aggregation** (the opposite of Responses' "the final state carries the complete value"). **All protocol differences converge in the adapter layer,
   `Message` is unchanged** -- this is exactly the purpose of layering.

**7. Acceptance**

1. The semantics of `ToolDefinition.parameters` are clarified as "protocol-agnostic JSON Schema" (it is standard
   JSON Schema to begin with, not OpenAI-private), and protocol differences converge in one place, `encode_tool_schema`.
2. Adding a protocol only requires implementing `MessageCodec` + `encode_tool_schema`, without changing the `Message` / `Tool` definitions.
3. The existing `bash` / `read` tools behave unchanged after the rework (protected by regression tests).
